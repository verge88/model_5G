# Аудит исходников Open5GS v2.8.0

База: `157f611a530e292e40ec50f9d23f0ef5d4fcd6a6`, tag object
`f2808a2fe0accd438008ff0564fe9ff4bba3d6ae`. Дата проверки: 2026-09-30.

## Исправления к исходному обсуждению

1. `src/smf/smf-sm.c:1284` уже присваивает `smf_instance_get_load()` полю
   собственного NF перед обработкой SBI timers, включая heartbeat. Поэтому
   утверждение о постоянно нулевом load неверно. Начальный ноль возможен,
   а округление целочисленной доли большого пула скрывает малые нагрузки.
2. `src/smf/context.c:3623` вычисляет долю allocated contexts в session pool.
   Это не измерение CPU и не калиброванная абсолютная ёмкость SMF.
3. `src/nrf/nnrf-handler.c:351` действительно игнорирует PATCH `/load`.
4. `lib/sbi/context.c:1424` возвращает первый matching NF. Из этого нельзя
   без измерений выводить фактическое распределение новых PDU sessions.
5. `src/smf/nsmf-handler.c:293` увеличивает `sessionnbr` ещё при обработке
   CreateSMContext; success counter увеличивается отдельно в
   `src/smf/sbi-path.c:356`. Следовательно, `sessionnbr` не является
   безусловным доказательством завершённого установления пользовательской сессии.

В статье необходимо различать allocated context, успешный CreateSMContext
и завершённое PDU Session Establishment. SCP видит SBI-контекст, но не
может одним HTTP 201 подтвердить работоспособность пользовательского тракта.

SWRR с весом `capacity*(100-load)` — экспериментальная политика, использующая
параметры 3GPP, а не единственный алгоритм, предписанный стандартом.
