# Специализированный детектор подмены NF-кэша AUSF

**Статус на 10.10.2026:** реализован исследовательский прототип: извлечение признаков, обучение ML, калибровка, проверка на отложенной выборке и выдача решений. Пройдены 15 программных тестов. Обученной на реальной атаке модели пока нет. Синтетические тесты не являются экспериментальным доказательством эффективности.

## Угроза и границы применимости

Основание — [официальное advisory Open5GS GHSA-fvpc-gmgr-qrg3](https://github.com/open5gs/open5gs/security/advisories/GHSA-fvpc-gmgr-qrg3). В описанном случае поддельное NFStatusNotify меняло локальное представление AUSF об UDM и направляло запросы аутентификации к постороннему endpoint, хотя профиль NRF не менялся. Advisory указывает Open5GS 2.7.7. Воспроизводимость на нашем стенде 2.8.0 пока не установлена.

Детектор проверяет согласованность **UDM / nudm-ueau** для каждого экземпляра AUSF. Он не использует данные прежнего эксперимента о нагрузке SMF: это другая угроза и другая задача обучения.

Основная мера защиты — проверять доверенный источник уведомления и его связь с действующей подпиской. Детектор дополняет эту проверку, но не заменяет её. В прототипе нет блокировки запросов или автоматического изменения NF-кэша.

## Метод

Сопоставляются пять потоков: независимый снимок NRF, снимок кэша AUSF, наблюдаемый маршрут запроса, входящие уведомления и действующие подписки. Для каждой секунды строится 25 признаков: доступность источников, число независимых доменов наблюдения, несовпадения endpoint, длительность несовпадений, изменения за последние 30 секунд, свежесть данных, неподтверждённые уведомления и конфликты наблюдателей.

Признаки описывают отношения и время. IP, hostname, идентификатор запуска, seed, метки атаки и абонентские идентификаторы не входят в ML-матрицу. Адреса нужны только для локального сопоставления множеств. Имя consumer служит ключом состояния и не передаётся модели.

Решение состоит из двух независимых частей:

1. Правила фиксируют удостоверенный недопустимый источник, отсутствие действующей подписки либо устойчивое расхождение кэша/маршрута с NRF. По умолчанию допустимая задержка сходимости — 5 секунд.
2. Специализированный ML оценивает сочетание признаков и их недавнюю историю. Используется градиентный бустинг с небольшими деревьями. Неизвестные значения кодируются отдельным значением −1 и индикаторами пропусков; они не превращаются в нули. Обучение уравновешивает классы и вклад независимых запусков внутри класса.

Специализация находится в причинных признаках, учёте происхождения данных и калибровке для разных наборов доступных наблюдений. Новый алгоритм бустинга не заявляется. Дополнительно обучается Isolation Forest только на честных данных как базовая ML-модель.

Гипотеза о пользе ML: сочетание коротких расхождений, смены маршрута после уведомления и неполной телеметрии может позволить обнаруживать подозрительное поведение раньше устойчивого порога. Это предстоит проверить. При полном достоверном наблюдении простое правило может оказаться достаточным.

## Доверие и ограничения

`observer_config.json` задаёт инвентарь коллекторов, их роли и домены доверия. **Этот файл не обеспечивает аутентификацию.** Внешний адаптер обязан удостоверять отправителя, защищать доставку и назначать `source` по проверенной личности коллектора. Принимать произвольный JSON от SBI-клиента нельзя.

`sender_verified` — результат независимой проверки транспортного источника уведомления, а не поле его тела. Значение `null` означает отсутствие подтверждения в любую сторону. `false` допустимо только после достоверной проверки, установившей нарушение. `callback_context` адаптер связывает с фактическим callback и consumer; одного переданного атакующим идентификатора недостаточно.

Два процесса на одном скомпрометированном узле не становятся независимыми наблюдателями. Домены в примере необходимо скорректировать под реальную архитектуру. Если все наблюдения подконтрольны атакующему, этот метод не обеспечивает обнаружение.

Снимки NRF должны содержать разрешённые для данного consumer/service origin с учётом действующих ограничений обнаружения. Кэш должен содержать origin именно соответствующей службы. Сравнение производится на уровне `(scheme, hostname, port)`; версия API, путь, сертификат и подмена между NF с одинаковым origin сейчас не различаются. При SCP нужны логический целевой origin и фактически выбранный upstream, а не просто адрес прокси; текущий адаптер должен выдавать канонический origin сервиса. DNS/IP соответствия требуется нормализовать доверенным адаптером до этого этапа.

Поддерживаются полные снимки. Частичный ответ нельзя объявлять полным: это создаёт ложные несовпадения. Значение TTL по умолчанию 15 секунд — экспериментальный параметр, требующий проверки. Состояние каждой роли становится неизвестным после истечения TTL, ошибки наблюдателя или конфликта её источников. Отсутствие уведомления не считается доказанным отсутствием события: без свежего наблюдения эта роль становится неизвестной.

Для ML требуются минимум два домена, отсутствие конфликтов и наличие кэша или маршрута. Дополнительно нужен порог, откалиброванный для конкретной маски доступности. Выполнение этих условий ещё не гарантирует наблюдаемость любой атаки. Отказ от оценки нельзя засчитывать как правильное отсутствие тревоги.

## Формат телеметрии

Вход — JSONL: один объект на строку. Это **новый нормализованный формат**, а не готовый парсер обычных логов Open5GS. Коллекторы для реального стенда ещё необходимо подключить.

Общие поля:

```json
{"observed_at": 12.0, "source": "nrf-audit", "kind": "registry_snapshot", "entity": {"consumer": "lab1/ausf1/boot1", "nf_type": "UDM", "service": "nudm-ueau"}, "data": {"complete": true, "endpoints": ["http://udm.example:7777"]}}
```

`observed_at` — время приёма доверенным агрегатором на единой шкале в секундах. Поток поступает в неубывающем порядке. Поздно поступившие события не сортируют задним числом по времени атакуемого узла. `consumer` уникален для развёртывания и перезапуска AUSF, чтобы не переносить состояние между ними.

| kind | Содержимое data | Роль источника |
|---|---|---|
| registry_snapshot | `complete: true`, `endpoints: [origin, ...]` | registry |
| cache_snapshot | `complete: true`, `endpoints: [origin, ...]` | cache |
| route | `endpoint: origin` | route |
| subscription_snapshot | `complete: true`, `bindings: [{callback_context, valid_until}]` | subscription |
| notification | `endpoints: [...]`, `sender_verified: true/false/null`, `callback_context` | notify |
| health | `available: true/false` | собственная роль коллектора |

`valid_until` использует ту же шкалу времени. Пустой полный снимок подписок означает установленное отсутствие подписок; отсутствие самого снимка означает неизвестность. Имена context не входят в признаки. Не включать SUPI/SUCI, AuthenticationInfo, ключи или векторы аутентификации.

Фиксированные временные отсчёты используют только уже полученные события. Все события с равным временем обрабатываются до соответствующего отсчёта. Для оценки во время отсутствия SBI-трафика коллектор передаёт достоверные `health`-события; heartbeat не продлевает свежесть старого снимка. Последний отсчёт ограничен концом входного потока.

## Запуск

Команды ниже выполняются из корня проекта в PowerShell. Используется существующая `.venv-analysis` с numpy, scikit-learn и joblib.

```powershell
.\.venv-analysis\Scripts\python.exe -m unittest discover -s experiments/nf_cache_detector -p test_detector.py -v

.\.venv-analysis\Scripts\python.exe experiments/nf_cache_detector/detector.py --events telemetry.jsonl --config experiments/nf_cache_detector/observer_config.json --output features.jsonl

.\.venv-analysis\Scripts\python.exe experiments/nf_cache_detector/model.py train --dataset dataset/manifest.json --config experiments/nf_cache_detector/observer_config.json --out models/nf-cache-v1

.\.venv-analysis\Scripts\python.exe experiments/nf_cache_detector/model.py score --features features.jsonl --config experiments/nf_cache_detector/observer_config.json --model-dir models/nf-cache-v1 --out decisions.jsonl
```

Первые два шага работают без обученной модели. Последние два требуют нового реального датасета. Тесты создают временную синтетическую модель и удаляют её; она не поставляется как модель для применения.

Выходные статусы: `protocol_violation`, `semantic_inconsistency`, `ml_suspected`, `no_alarm`, `insufficient_evidence`. Поля `rules_alarm` и `ml_alarm` сохраняются отдельно; `ml_alarm: null` означает отказ. Число `score` — оценка модели, не доказанная вероятность атаки. Статус имеет приоритет правил, поэтому отсутствие пригодной ML-оценки не скрывает уже установленное нарушение.

## Обучение и воспроизводимость

`manifest.json` задаёт файлы и разделение по целым независимым запускам:

```json
{"runs": [
  {"run_id": "train-honest-1", "seed": 101, "split": "train", "features": "train-honest-1.features.jsonl", "labels": "train-honest-1.labels.jsonl"},
  {"run_id": "train-attack-1", "seed": 102, "split": "train", "features": "train-attack-1.features.jsonl", "labels": "train-attack-1.labels.jsonl"},
  {"run_id": "cal-honest-1", "seed": 201, "split": "calibration", "features": "cal-honest-1.features.jsonl", "labels": "cal-honest-1.labels.jsonl"},
  {"run_id": "test-1", "seed": 301, "split": "test", "features": "test-1.features.jsonl", "labels": "test-1.labels.jsonl"}
]}
```

Это сокращённая схема, а не достаточный объём калибровки. Метки хранятся отдельно: `{"observed_at": 12.0, "entity": {...}, "label": 0}`. Значения: 0 — честное состояние, 1 — подтверждённое атакованное состояние, null — неоднозначный интервал, исключённый из обучения и оценки. Необходимо точное соответствие времени/entity каждому вектору. Определение атакованного состояния фиксируют заранее: отправка попытки и состоявшееся отравление кэша — разные события.

Код запрещает пересечение seed между train/calibration/test и повтор run_id. Исследователь дополнительно объединяет связанные пары и производные копии одного захвата в одну группу seed; по именам файлов код не способен распознать скрытые копии.

Для каждой маски доступности требуется минимум 3 независимых честных калибровочных запуска и 1000 пригодных окон. Калибровка выбирает порог по эмпирической доле ложных тревог ≤0,1%; сравнение строгое `score > threshold`. Эти минимумы не означают статистическую гарантию FPR 0,1%: соседние окна коррелируют, и нужны доверительные интервалы по независимым запускам. Новые маски без обучения/калибровки приводят к отказу.

Сохраняются `model.joblib`, `freeze.json` с параметрами, версиями и хешами входов, а также `test-evaluation.json` с показателями по запускам. Конфигурация наблюдателей связана хешем с признаками и моделью. Существующую модель нельзя молча перезаписать. Joblib загружать только из доверенного локального источника: хеш проверяет неизменность, но не удостоверяет происхождение файла.

Оценка содержит результаты ML и правил на тех же пригодных окнах, полное покрытие и отказы. Доверительные интервалы по запускам, задержка до обнаружения относительно начала отравления и первого отказа аутентификации требуют последующего анализа с независимой разметкой эпизодов; эта часть здесь не реализована.

## Следующий реальный эксперимент

1. Зафиксировать изолированную версию и подтвердить именно механизм advisory. Не переносить вывод о 2.7.7 автоматически на 2.8.0.
2. Подключить защищённые коллекторы NRF, подписок, AUSF-кэша и маршрутов; удостовериться, что наблюдатели видят разные границы доверия. Сначала проверить согласованность на честном трафике.
3. Собрать честные регистрации, смены профиля, перезапуски, failover, масштабирование и задержки доставки наблюдений. Отдельно собрать подтверждённые эпизоды подмены кэша в разрешённом лабораторном окружении.
4. Проверить полное наблюдение, потерю каждого источника, задержки, временные конфликты и недоступность наблюдателей. Пропуски и интенсивность трафика распределять сопоставимо между классами, иначе ML выучит устройство эксперимента.
5. Разделить независимые запуски до настройки модели. Менять адреса и имена между запусками; новые сочетания нагрузки и задержек оставить для проверки переноса. Условия будущего теста не использовать для выбора признаков и порогов.
6. Сравнить проверку источника/подписки, устойчивое правило согласованности, Isolation Forest и специализированный ML. Измерить recall при фактически измеренном FPR, покрытие, задержку и вычислительные затраты. Для гибридного решения считать общую частоту тревог отдельно: калибровка ML не ограничивает FPR правил.
7. Проверить вклад групп признаков: без уведомлений, без подписок, без кэша, без истории. Преимущество ML признавать только на отложенных независимых данных при сопоставимом FPR и покрытии. Если правило оказывается не хуже, сохранить этот результат.

Пакет не подключён к работающему стенду, не обучен на новой реальной угрозе и не является готовым сервисом постоянного мониторинга. Для такого сервиса также нужны управление объёмом состояния, сохранение состояния между перезапусками, ограничение размера входных сообщений и эксплуатационная проверка адаптеров.

## Обучение в GitHub Actions

Отдельная ветка: `codex/nf-cache-detector-actions`. Workflow: `.github/workflows/nf-cache-training.yml`, имя **NF cache detector training**. Он автоматически запускается при push изменений детектора или workflow в эту ветку. Основная ветка не изменяется. `workflow_dispatch` также описан; до появления workflow в default branch кнопка ручного запуска может быть недоступна. В текущей ветке повторный запуск выполняется через **Re-run all jobs** существующего запуска либо через новый commit с изменением `training_request.json`.

Конфигурация обучения хранится в `training_request.json`, поэтому она версионируется вместе с кодом. По умолчанию выбран `synthetic-bootstrap`: автономный генератор событий, который не запускает Open5GS, не посылает сетевые запросы и не воспроизводит эксплуатацию уязвимости. Метки задаются внутренним состоянием симулятора, а признаки вычисляются обычным причинным экстрактором из отдельного потока событий.

Шесть сценариев: стабильная работа, законная смена endpoint, failover, длительное, краткое и периодическое отравление кэша. Четыре режима наблюдения: полный, без кэша, без NRF, без уведомлений. В train используются 4 группы seed, в честной калибровке 3, в test 3. Всего 204 трассы по 241 отсчёту: 96 train, 36 calibration, 72 test. Адреса меняются между seed; производные сценарии одной группы остаются в одном разделе. Синтетическая модель сильно упрощает доставку сообщений и повторяет refresh каждые 10 секунд; перенос её результатов на реальную сеть недопустим.

Runner Ubuntu 24.04 использует Python 3.12 и версии библиотек из `requirements-ci.txt`. Лимит задания 30 минут, одновременно для ветки работает одно задание; новый commit не останавливает текущее обучение. Запускаются все `test_*.py` — на момент добавления workflow 20 тестов. Затем выполняются генерация, обучение обеих моделей, калибровка и оценка; отсутствие пригодных калиброванных масок считается ошибкой, а не успешным обучением.

В разделе **Actions → NF cache detector training → выбранный запуск** доступны:

- **Summary** с происхождением данных, числом пригодных окон, отказами и тревогами моделей и правил;
- логи тестов и обучения;
- архив `nf-cache-training-<run_id>-<attempt>` с моделью, freeze, оценкой по запускам, версионированным manifest, происхождением обучения и средой выполнения. Для синтетического режима сохраняются также события, признаки и метки. Срок хранения артефакта — 30 дней.

В `model.joblib`, `freeze.json` и `training-run.json` указано `data_origin: synthetic-bootstrap`; такая модель не считается обученной на реальной угрозе. Обозначение нельзя менять вручную, чтобы представить синтетические результаты как реальные.

Для локального повторения того же задания:

```powershell
.\.venv-analysis\Scripts\python.exe experiments/nf_cache_detector/run_training.py --out tmp/nf-cache-training-new
```

Выходная папка должна быть новой. Для точного соответствия CI нужно отдельное окружение Python 3.12 с `requirements-ci.txt`; существующее окружение локального стенда автоматически не изменяется.

### Переключение на реальные трассы

Сначала собрать и обезличить телеметрию новой угрозы по описанному выше протоколу. Репозиторий публичный: для выбранного способа передачи подходят только данные, предназначенные для публикации. Разместить manifest, features и labels под `experiments/nf_cache_detector/datasets/<version>/`; именно каталог детектора загружается в runner. Пути участников manifest должны оставаться внутри его каталога. Все признаки должны быть вычислены с текущим `observer_config.json`.

В manifest добавить `"data_origin": "real-capture"` и непустой объект `"provenance"` с версией/commit Open5GS, идентификаторами сборщиков, способом подтверждения отравления, датой захвата и описанием разметки. Это заявление автора данных: workflow проверяет наличие, но не способен удостоверить реальность эксперимента. Train/calibration/test и seed должны соблюдать прежние ограничения; калибровка содержит только честные состояния.

Затем заменить конфигурацию запроса:

```json
{
  "mode": "real-capture",
  "manifest": "experiments/nf_cache_detector/datasets/capture-v1/manifest.json"
}
```

Commit и push в отдельную ветку запустят обучение. При отсутствии данных, неправильном происхождении или недостаточной калибровке запуск завершится ошибкой. Подстановка синтетики вместо отсутствующих реальных данных запрещена в коде.
